# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

This repo defines and evolves the **Open Knowledge Format (OKF)** (`WIKI_SPEC.md`, version 0.3), holds a real OKF knowledge bundle (`vault/`), holds the local-only tool that produces and serves that bundle (`pipeline/`), and holds a conversational agent that reads it (`agent/`).

OKF is a minimal, agent- and human-friendly format for representing knowledge: a directory tree of markdown files with YAML frontmatter, designed to be authored by people, generated by agents, and consumed by both, with no required tooling or schema registry.

Four things live here, each with a different scope:

- **`WIKI_SPEC.md`** — the normative spec. Source of truth for what makes content conformant; see "Working with the spec" below.
- **`vault/`** — an actual OKF bundle (also an Obsidian vault) conforming to that spec; see "The vault" below.
- **`pipeline/`** — a hexagonal-architecture Python tool (Ollama + ChromaDB + SQLite, all local) that watches `vault/raw/`, turns unprocessed notes/documents into conformant concepts in `vault/`, indexes them for hybrid search (vector + lexical + graph-expansion — see `pipeline/docs/architecture/data-flow.md`), and serves the vault to MCP clients (e.g. Claude) over a stateless Streamable HTTP MCP server. It has its own docs — start at `pipeline/README.md`, then `pipeline/docs/` (an MkDocs site: architecture, domain model, CLI/MCP/config reference, dev onboarding). Treat those as authoritative for anything about the pipeline's code; this file only covers the OKF spec and vault conventions.
- **`agent/`** — a Google ADK-based conversational Knowledge Retrieval Agent, a separate deployable that reads the vault entirely through `pipeline`'s MCP server (no direct vault access, no write-back). See `agent/README.md`.

## Working with the spec

`WIKI_SPEC.md` is self-contained and normative. When asked to author or validate OKF content (a "knowledge bundle"), treat this file as the source of truth rather than inferring conventions from examples elsewhere. Key structural points to keep straight when editing the spec or producing content against it:

- **Bundle**: a directory tree of markdown files. **Concept**: one markdown document = one unit of knowledge; its ID is its file path minus `.md`.
- **Reserved filenames**: `index.md` (directory listing, §8) and `log.md` (chronological update history, §9) — never used for concept documents. All other `.md` files are concepts.
- **Concept documents** = YAML frontmatter (delimited by `---`) + markdown body. `type` is the only required frontmatter key; everything else (`title`, `description`, `resource`, `tags`, provenance/trust/lifecycle fields) is optional, and unrecognized keys/types MUST be tolerated, not rejected (§11, conformance).
- **Provenance/trust/lifecycle families** (§5): `sources` (with per-source credibility signals `author`, `usage_count`, `last_modified`, plus `id` and `locator` for per-passage attribution — several entries MAY share one `resource`, distinguished by `id`, which MUST be unique within a concept), `generated: { by, at }`, `verified: [{ by, at }]` (derives a trust tier: unverified / machine-confirmed / human-reviewed), `status` (draft/stable/deprecated), `stale_after` (absolute date).
- **Actor convention** (§7): `<producer>/<version>` for agents, `human:<id>` for people, `process:<id>` for automated processes. Trust-tier classification keys off the `human:` prefix specifically.
- **Cross-linking** (§6): standard markdown links; bundle-relative links start with `/` and are the recommended form. Broken links are tolerated, not errors.
- **Attested Computation** (§10): a distinct concept type (`type: Attested Computation`) that pairs a sanctioned computation (`runtime`, `parameters`, `computation`) with an `executor` (runs it, returns a receipt) and an `attester` (deterministic, no-LLM code that verifies a receipt against the contract). This is how the format distinguishes "this number was produced the right way" (attestation) from "this definition was reviewed" (`verified`) — §10.6 spells out the distinction explicitly.

When modifying the spec itself, preserve its versioning discipline (§12): minor bumps are additive/backward-compatible only; anything that renames a required field or changes reserved filenames is a major bump and must be called out in a "Changes from vX.Y" section like §13.

## The vault

`vault/` is the OKF bundle: an Obsidian vault whose contents are also a conformant OKF bundle. Structure:

- `vault/index.md` — the bundle-root mechanical directory listing (§8), carrying `okf_version: "0.3"`.
- `vault/Home.md` — the curated, thematic entry point (`type: MOC`), separate from `index.md` on purpose: `index.md` lists what physically exists in a directory; a MOC hand-curates links across the bundle by theme, independent of folder placement. Named `Home.md` for its role, not `MOC.md` for its type — the same way future sub-MOCs get named after their theme.
- `vault/references/` — external material, run instructions, or code that concepts cite via `sources[].resource`, `executor.resource`, or `attester.resource` (§6.3). Has its own `index.md`. No longer purely manual: the first time `pipeline` parses a source document (PDF/PPTX/etc. dropped in `vault/raw/`), it auto-creates a `references/<slug>.md` stub (`type: Source Document`) representing that document, and every concept later extracted from its chunks gets a `sources[]` entry pointing back at it — see `pipeline/docs/architecture/data-flow.md`'s `ParseSourceDocuments`/`IngestRawMaterial` sections.
- `vault/raw/` — **not** part of the OKF bundle. A Karpathy-style capture inbox for unprocessed material (chat dumps, clippings, notes) awaiting distillation into real concepts. Files here carry no frontmatter and are never linked to from finished concepts. This is exactly what `pipeline/` watches and distills — see `pipeline/docs/architecture/data-flow.md` for the full scan → parse → ingest → index trace.

This bundle deliberately does not have a `log.md`: `log.md` (§9) is optional ("MAY appear"), and the pipeline's ingest audit trail (create/merge/reject decisions) is pipeline governance state, not vault knowledge — it lives in the pipeline's SQLite store (`bundle_log` table) instead, queryable via `pipeline log`, the `okf://log` MCP resource, or `pipeline/docs/architecture/ports-and-adapters.md`'s `BundleLogPort`.

`index.md` files are never concepts and are never graph participants: they carry no `type` (no frontmatter at all, besides the bundle-root's `okf_version`), `MarkdownConceptRepository.list()` skips them, and they never get embedded or appear in the pipeline's `links`/`concepts` SQLite tables. They exist purely for progressive disclosure (§8) — a mechanical, per-directory table of contents linking *out* to concepts, not something concepts should link back to as a "related concept."

No topical folders (work/health/projects/...) are pre-created — the spec deliberately leaves directory structure to the producer (§3), so folders get added organically as concepts accumulate, not designed upfront.

### MOCs and MOCs of MOCs

`type: MOC` is a producer-defined concept type (not part of the OKF spec itself) for Maps of Content: a concept whose body is a curated set of links on a theme, cutting across the directory hierarchy rather than following it. MOCs can link to other MOCs ("MOCs of MOCs") to build a navigable hierarchy that lives entirely in the link graph (§6), orthogonal to the physical folder tree. Do not add `type: MOC` (or any frontmatter beyond the root's `okf_version`) to `index.md` files — that would repurpose a reserved filename as a concept document, which §3.1/§8 rule out; keep the two mechanisms separate (`index.md` = mechanical listing, `Home.md` = curated hub).

### Categories: a Wikipedia-style ontology layer under Domains

`type: Category` is another producer-defined concept type, living under `vault/categories/`, forming a finer-grained tier underneath `type: Domain` — a `Domain` like "Coffee" might have Categories like "Brewing Methods" or "Equipment". Unlike MOCs (hand-curated), Category membership is machine-derived: `pipeline`'s `KnowledgeAgent` classifies each new concept into zero or more existing Categories (or proposes new ones) at ingest time, and `pipeline categorize` backfills concepts that predate this feature. A concept links to its Categories the same way it links to anything else (§6, under a `## Categories` heading), and a Category links to exactly one parent (a Domain or a broader Category) — a forest rooted at Domains, not a full multi-parent DAG. Because it's just §6 links, this ontology rides on the same link graph everything else does; `pipeline`'s hybrid search uses it as a graph-expansion signal (see `pipeline/docs/architecture/data-flow.md`'s Search section) — a concept's Category acts as a bridge to its topical siblings even when they share no vocabulary or embedding similarity.

### Typed relations: naming *how* two concepts are connected

Plain §6 links (and Category links above) say two concepts are connected but not *how* — for lineage/impact questions ("was this decision superseded?") the edge's meaning matters. The convention for that is a Dataview-style inline field, written as its own line in the body: `relation_type:: [[target]]`, e.g. `supersedes:: [[/decisions/old-decision]]`. This isn't an OKF spec mechanism, and it isn't invented from scratch either — it's the same `key:: value` convention the Obsidian ecosystem's Dataview/Breadcrumbs plugins already use, so it renders as an ordinary wikilink in Obsidian's native graph/backlinks with no plugin required just to see the connection. Every typed link is also an ordinary untyped link (it's tracked in both `pipeline`'s `links` and `typed_links` SQLite tables) — typed relations are a superset signal layered on top of the plain link graph, not a separate one. `pipeline lineage <concept-id>` / the `trace_lineage` MCP tool walk these edges to reconstruct a chain (e.g. decision → superseded_by → decision), not just confirm one hop exists.

### Versioning convention

Don't invent a separate version/timestamp field. Use what the spec already provides:

- `generated: { by, at }` on a concept records its last meaningful content change — this is the timestamp (§5.2), and it deliberately supersedes the old v0.1 bare `timestamp` field (§13.1).
- `verified: [{ by, at }]` separately records confirmation events, independent of `generated.at` (content can change without re-confirmation, and vice versa).
- Full version history comes from git (commit log) — the spec recommends git as the bundle's distribution form specifically because it provides history, attribution, and diffs (§3). `log.md` (§9) would normally be a curated, human-readable summary layer on top of that history; this bundle keeps that layer in the pipeline's SQLite audit trail instead (see "The vault" above).

## Conformance rules to respect when generating bundle content

A bundle is conformant if every non-reserved `.md` file has parseable YAML frontmatter with a non-empty `type`, and reserved files follow §8/§9 when present (§11). Concretely, when producing concept files:

- Never invent a required field beyond `type` — everything else is optional by design.
- Don't reject or "fix" unknown `type` values or unknown frontmatter keys in existing content; the format is intentionally permissive.
- Use bundle-relative links (`/path/to/concept.md`) over relative ones where practical, since they survive the concept being moved within its subdirectory.
- For per-claim attribution, use markdown footnotes keyed to `sources[].id`, not a body citations list (the `# Citations` heading is a deprecated v0.1 pattern, §13.1). `pipeline` writes these automatically: one `sources[]` entry per contributing passage, a `[^id]` marker on the text that passage produced, and the definitions under a `## Sources` heading kept *before* any trailing link section.

## Working with git history

Never do a heavy rewrite of git history — reconstructing intermediate commits, rebasing, amending already-shared commits — without asking first, even when it looks like the cleanest way to fix something. Ask before, not after.
